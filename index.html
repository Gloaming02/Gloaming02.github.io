Intuit · Mountain View, CA

Software Engineer — TurboTax AI Agent Platform

Most of what I do is evaluation, and evaluation is not one script at the end of a run. It stretches the length of the release: an LLM-as-a-judge framework scoring agent output on accuracy, relevance, completeness and coherence; local pre-release runs before a change leaves a laptop; online E2E and PRD runs against the real stack; and routing-correctness checks that catch a personalized question being handed to a general-purpose skill — a failure aggregate accuracy will never show you. Most of the time the eval is the debugger: a failing case doesn't hand you a grade, it hands you a diagnosis — which skill, which route, which step gave up.

With an AI scientist I built a shared eval library so teams measure the same way, and tuned the automated routing evaluation until it agreed with the production planner/router 80–85% of the time. That number is the whole exercise: an offline eval nobody trusts is worse than no eval, because it hands you confidence you haven't earned. And it doesn't stop at launch — once an agent is stable we pull real traffic out of production monitoring, sample it, and keep scoring against it, so quality stays a measured thing rather than an assumption that ages badly.

I wrote the first skill on the platform, then turned that into a self-service authoring framework — templates, metadata-driven routing, and evaluation guidance built in — so other teams could ship skills without coming through me. One of them is TurboTax CoPilot's general help and FAQ skill, backed by retrieval-augmented search.

Underneath all of it: migrating a legacy multi-agent system onto modular, independently testable skills; scoped agent identity authentication on the backend REST services behind a feature flag; standardized error and response envelopes with traceId and agentId lifted into shared middleware; and Jenkins integration-test gates, Argo CD deploys, Splunk alerting and Langfuse tracing so agent behaviour can be diagnosed end to end.

OpenArt

Software Engineer — generative video quality

Three months on the OpenArt build, working on output quality rather than plumbing. Generating a clip is the easy part; generating one that holds together is not. A face has to stay the same face across every shot, a visual style has to survive eight scene changes, and the seam between two clips has to not announce itself. That work lives in character and style anchors, environment references, and keyframe extraction that gives the next scene something to start from.

The music-video pipeline starts from the song instead of a prompt. Audio analysis pulls tempo, beats and section boundaries out of the track so cuts land on the beat rather than on a timer, and the director pass builds a story arc and a style bible over that timeline — then character generation, keyframe-to-segment mapping, lip sync, and an ffmpeg assembly that lays the original audio back over the cut.

Every change had to answer to the eval. We built an auto-rater framework that scores the pipeline stage by stage rather than only judging the finished video — separate raters on a 1–5 rubric for the storyline, the character reference, the scene prompt, the keyframes, each generated clip and the final cut, with a second set for music videos covering creative blueprint, shot list, performer reference and sentiment match. Where a number could be measured instead of judged, it was: cut precision against detected beats, and LSE-D / LSE-C for lip sync.

Batch runs pull their cases from a sheet and write grades into Postgres, so changing prompt composition or keyframe logic shows up as a score moving on a specific stage — rather than a vague sense that the videos look better this week.

02 — AI
CS 5100 · decision-making under hidden information

Texas Hold'em Agents

Two-person project · engine, agents and evaluation built from scratch

Chess is tractable because you can see the board; poker is not. We built a two-player Hold'em engine from scratch and put five agents on it — random, never-fold, rule-based, a Monte Carlo hand-strength estimator, and an MCTS player that simulates forward and takes the branch with the best average return.

The finding was about the benchmark, not the agents. Our first harness scored a fold as a loss, so over 10,000 hands the rule-based player came out level with one that never folds — which cannot be true. The metric was wrong: counting folds as losses made disciplined folding invisible. Rebuilt around chip depletion, the ranking inverted. MCTS then placed third, behind the simpler estimator and against our own hypothesis — and we reported that rather than tuning until the numbers agreed with us.

About

The short version

I like the unglamorous parts — the eval harness, the fallback path, the thing that tells you why it broke at 3am.

My day job is LLM agent infrastructure: taking agent systems that work in a notebook and giving them the structure to survive production — composable skills, measurable output, scoped identity, a release path with teeth.

Evaluation is the part I've gone deepest on, and I think it gets misread as a report card. A score at the end of a run is the least of what it does. Eval is how you debug an agent — a failing case is a diagnosis, not a grade. It's how quality actually moves, because you cannot improve what you cannot see. And it doesn't end at launch: once an agent is stable, you sample real traffic back out of production and keep scoring it, because what was right last release isn't automatically right this one.

Which makes the hard part obvious in hindsight. Building the harness was never it. Getting the harness to agree with production closely enough that people act on what it says — that's the work.

Outside work I ship game-automation tools, mostly because a problem you can watch succeed or fail on screen is a very honest test.
